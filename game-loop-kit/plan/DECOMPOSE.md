# DECOMPOSE — spec을 Plan → Task → Ticket으로 배분하는 규칙

> **입력:** 채워진 `spec/`(INTAKE 답 → GDD·systems·assets)
> **출력:** `plan/PLANS.md` + `PLAN-NN/PLAN.md` + `tasks/TASK-NN.MM.md`(티켓 포함)
> **참고 하네스:** `workflow-map-systems`(컨셉→시스템), `template-systems-index`, superpowers `writing-plans` → `HARNESS.md`

## 1. 배분 원칙 (무엇이 무엇이 되나)
| spec의 것 | 계층 | 규칙 |
|---|---|---|
| **시스템 하나** (systems/*.md) | **Plan** | 게임을 성립시키는 메카닉 단위 (예: 핵심 감지 시스템, 클래스 밸런스) |
| **그 시스템의 국면** | **Task** | 구현 순서상 한 덩어리 (예: 피드백 채널 하나, 튜닝 패스) |
| **한 번의 검증 사이클로 끝나는 일** | **Ticket** | 아래 §2 크기 규칙 |

**우선순위:** Core Verb·30초 루프에 가장 가까운 시스템이 PLAN-01. 그 다음 5분→세션→진행 루프 순.
**MVP 경계 밖**은 Plan을 만들되 `status: parked`.

## 2. 티켓 크기 규칙 (해상도)
INTAKE Phase 6의 답을 기본값으로. 없으면 이 기본:
- **한 티켓 = 한 번의 구조검증 + 한 번의 행동검증으로 끝나는 크기.**
- 티켓 하나에 **관측 가능한 행동 하나**. ("심박이 거리별로 바뀐다" ⭕ / "살기감지 시스템 완성" ❌)
- 산출물이 **파일 1~2개 + 디바이스 배치/배선 몇 개**를 넘으면 → 쪼갠다.
- 수치 튜닝은 **별도 티켓**(구현과 분리해야 검증이 깨끗함).
- **GUI 전용 단계**(새 @editable 배선 등)는 **독립 티켓**으로 떼고 `blocked` 표시 → 정지게이트.

## 3. 티켓 수용기준 만드는 법 ⭐
각 티켓은 반드시 **둘 다** 갖는다.
- **구조 수용** ← systems/의 *구성* 규칙에서 파생. "무엇이 배치·배선·설정돼야 하나."
  (uefn-inspector로 확인 가능한 말로 쓴다 — 배치·배선·값·참조)
- **행동 수용** ← systems/의 *행동* 규칙에서 파생. "실행하면 무엇이 관측되나."
  (PIE 로그/상태로 확인 가능한 말로 — 그래서 Verse에 Debug 로그를 심는다)

> 수용기준이 **관측 가능한 말로 안 써지면** = 스펙이 덜 정해진 것 → INTAKE/systems로 되돌아간다.

## 4. 의존성·순서
- `deps:`에 선행 티켓 ID. **감각 피드백 → 규칙 → 튜닝** 순이 보통 안전.
- 프로토타입이 필요한 **최대 리스크**(INTAKE Phase 2)는 **초기 Plan의 첫 Task**로 올린다.

## 5. 배분 절차
1. systems/ 목록 → Plan 후보 나열, Core Verb 근접도로 정렬 → `PLANS.md`
2. 각 Plan → 국면별 Task 3~6개 → `PLAN-NN/PLAN.md` 표
3. 각 Task → 티켓 2~6개 (§2 크기) → `tasks/TASK-NN.MM.md`
4. 각 티켓에 §3 수용기준 + 산출물 + deps 기입
5. 검토: **모든 티켓이 §2 크기? 수용기준이 관측 가능? GUI 전용은 분리됐나?**

## 6. 재분해 트리거
- 티켓이 **행동검증 3회 실패** → 너무 큼, 쪼갠다
- 드리프트 발견(선언↔배선 불일치 등) → **드리프트 티켓** 신설
- 플레이테스트로 스펙 변경 → `workflow-propagate-design-change`로 spec→plan 전파
